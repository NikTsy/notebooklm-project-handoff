---
name: notebooklm-project-handoff
description: Retrieve a project fact missing from the supplied handoff and relevant local files, or maintain and publish the project summary for a requested push, merge, or new handoff.
---

Use `PROJECT_CONTEXT.md` as the project summary. This is a file maintained by the project, so create it during setup or the first requested handoff if it is missing. For a read-only question, fall back to the README and relevant files. Check the relevant Git diff and existing summary sections. Update the paragraph that owns a changed fact and add only durable decisions, verified status, and open work. Distinguish working-tree changes from deployed behavior. Exclude credentials and private logs from the summary.

For a push, bring the relevant README sections up to date and include documentation changes in the push. For a requested merge, update the relevant project documentation and summary from the diff, include those updates in the merge, then publish the summary from the resulting target branch after the merge succeeds. If the merge is blocked, report its status and keep the published summary accurate. For a handoff, write a short continuation brief after updating and publishing the summary. Include the few verified facts the next step depends on directly in that brief, with provenance where helpful. Push only when the user has requested it.

From the target project root, run `python3 <skill-directory>/scripts/publish.py`. The config lives at `.notebooklm-handoff/config.json`. Use the configured note or Google Doc as the single managed copy. Repeated runs with unchanged content and destination skip the network. Treat `Unchanged` as complete for routine runs. A published hash confirms delivery to the configured destination. If the user requests a NotebookLM check, open the existing source and verify the changed facts there.

For questions in a new chat, start with `AGENTS.md` and any handoff provided by the user. Use the handoff for the task goal, recent decisions, and next step, then consult the local summary. Verify handoff claims against current evidence when they affect the task. Open only relevant README or documentation sections for setup, operations, or design. Inspect targeted code for actual implementation behavior or to resolve discrepancies. Stop as soon as the handoff and local files answer the question. Query NotebookLM only for a material fact missing from both. Use `python3 <skill-directory>/scripts/lookup.py "term|synonym"` for a small local excerpt. If a configured note is needed, use `python3 <skill-directory>/scripts/lookup.py --note "term|synonym"`. It reads the note by ID and shows only matching lines, so the full note stays outside model context. If the excerpt is incomplete, try a synonym or inspect one relevant source. Do not list notebooks to resolve a configured ID. If only the notebook is identified, ask a focused question with `notebooklm ask --notebook NOTEBOOK_ID --json "focused question"`. Otherwise use a configured query connector or signed-in browser when available. Cite the source and report access failures or unconfirmed publication directly.

When updating the summary, capture newly confirmed answers that are likely to help future chats, especially stable facts that have required repeated lookup. Update the owning paragraph once and keep its provenance. Record an unanswered question as open only if it affects future work. Leave routine lookup misses out of the summary. When an attachment establishes a durable fact, such as a hardware model identified from a photo, capture the confirmed fact and a short provenance reference when available. Reuse the recorded fact in later chats. Reinspect the attachment when the evidence changed or the task requires visual details.
