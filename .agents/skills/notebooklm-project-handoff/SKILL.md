---
name: notebooklm-project-handoff
description: Maintain a repository's project summary and publish it to an existing NotebookLM note or Google Docs source during a push, merge, or handoff. Use for project continuity and concise session closeouts.
---

Use `PROJECT_CONTEXT.md` as the project summary. This is a file maintained by the project, so create it during setup or the first requested handoff if it is missing. For a read-only question, fall back to the README and relevant files. Check the relevant Git diff and existing summary sections. Update the paragraph that owns a changed fact and add only durable decisions, verified status, and open work. Distinguish working-tree changes from deployed behavior. Exclude credentials and private logs from the summary.

For a push, bring the relevant README sections up to date and include documentation changes in the push. For a requested merge, update the relevant project documentation and summary from the diff, include those updates in the merge, then publish the summary from the resulting target branch after the merge succeeds. If the merge is blocked, report its status and keep the published summary accurate. For a handoff, write a short continuation brief after updating and publishing the summary. Push only when the user has requested it.

From the target project root, run `python3 <skill-directory>/scripts/publish.py`. The config lives at `.notebooklm-handoff/config.json`. Use the configured note or Google Doc as the single managed copy. Repeated runs with unchanged content and destination skip the network. A published hash confirms delivery to the configured destination. If the user requests a NotebookLM check, open the existing source and verify the changed facts there.

For questions in a new chat, start with `AGENTS.md` and any handoff provided by the user. Use the handoff for the task goal, recent decisions, and next step, then consult the local summary. Verify handoff claims against current evidence when they affect the task. Open only relevant README or documentation sections for setup, operations, or design. Inspect targeted code for actual implementation behavior or to resolve discrepancies. Query NotebookLM only for a material gap or on explicit request. If the config has a `notebook_id` and the CLI is authenticated, use `notebooklm ask --notebook NOTEBOOK_ID --json "focused question"`, or read an identified note by ID with `notebooklm note get`. Otherwise use a configured query connector or signed-in browser when available. Cite the source and report access failures or unconfirmed publication directly.

When updating the summary, capture newly confirmed answers that are likely to help future chats. Record an unanswered question as open only if it affects future work. Leave routine lookup misses out of the summary.
